# UI

Owner: `ui-ux-engineer` with `nextjs-architect`. Requirements: `SZ-FUN-001`,
`SZ-PWA-003`, `SZ-SEC-002`, `SZ-SEC-007`.

## 1. The design constraint that is a security control

Most of this interface is ordinary admin UI. One screen is not: **the approval
screen** (`spec/09-pwa-approvals.md` §7). There, a visual compromise becomes a
security failure — a truncated digest makes two artefacts indistinguishable, and
an approve button reachable before the details have been read is an approve
button that gets pressed.

So the approval surface has rules the rest of the UI does not:

- The digest suffix is **never** truncated below the fixed length, at any
  viewport. The layout reflows; the evidence does not shrink.
- Actions sit **below** the bound details, and remain so at the largest supported
  system font. An approver who must scroll up to see what they are approving
  will not scroll up.
- Approve and reject are not adjacent, and reject is not the quiet option.

## 2. Visual system

shadcn/ui on Radix primitives, Tailwind, with a red accent. Dark mode is a first
-class theme, not an inversion — appliances live in racks and operations rooms
where dark is the default.

**Status is never conveyed by colour alone.** Every state carries a glyph and a
word as well: an operations room has bad monitors, and a meaningful fraction of
operators cannot distinguish the red and green we would otherwise rely on.

## 3. The two dashboards (`SZ-FUN-001`)

Covered in `spec/00-product.md` §4. The UI rule is that the two things most often
discovered too late — **certificate expiry** and **a DR HSM whose Key Check Value
no longer matches** — are persistent dashboard items, not entries in a report
somebody runs quarterly.

## 4. Server Components by default

The web tier renders untrusted input and holds a session, and it is the largest
dependency tree in the appliance. So:

- Server Components by default; client components where interaction requires it,
  and each one is a deliberate choice.
- Data access through typed server actions and route handlers. The browser never
  holds a database credential, and there is no generic query endpoint.
- **No secret reaches the client bundle.** Asserted by scanning the built output,
  not by convention (`SZ-SEC-005`).
- The web tier holds no device access and no root (`SZ-SEC-002`) — visible in the
  UI as the absence of anything resembling a terminal.

## 5. CSP, and why it has to be strict here

Per-request nonces, no `unsafe-inline`, no `unsafe-eval`. The appliance's UI is
where an approver makes a decision, and a script injected into that page can lie
about what is being approved (`spec/02-threat-model.md` §5 — the browser is only
partly trusted).

WebAuthn step-up narrows this: the assertion binds to the challenge derived from
the request, so a page that lied about the artefact cannot produce a valid
assertion for a different one.

## 6. Accessibility

WCAG 2.2 AA across the product, asserted with axe in both themes, and full
keyboard operation with a visible focus indicator.

On the approval screen this is not a compliance item: the bound details are
announced to a screen reader **before** the actions, in the order a sighted user
reads them. An approver using assistive technology must get the same evidence in
the same order, or they are approving something different from what the sighted
user approved.

## 7. Error states

Errors say what happened, why, and what to do. In particular:

- A `412` names the current state and what is required
  (`spec/07-rest-api.md` §1) — "the appliance is Locked; unlock it to continue",
  not "request failed".
- A policy denial names the rule (`spec/06-signing.md` §3).
- An expired request says so, rather than failing generically.

## 8. How this is verified

- Every field of `SZ-PWA-003` is visible at 320 px and at the largest system
  font, with actions below the details — asserted by screenshot, not review.
- The digest suffix is never shorter than the fixed length at any viewport.
- axe reports zero violations at WCAG 2.2 AA in both themes.
- The built client bundle contains no secret, scanned.
- CSP contains no `unsafe-inline` or `unsafe-eval`, and the app works without
  them.
- Every status indicator carries a glyph and a word as well as a colour.
- Screen-reader order on the approval screen presents details before actions.
