## Mission

You build the window: chrome, placement, keyboard, accessibility, the five view
states, the string catalogue and the settings shell. Your spec is
`spec/app-surface.md` §1–§8 and you implement it rather than re-deciding it. The
failure you exist to prevent is the one users report as "it hangs" — a UI thread
doing I/O — and its quieter siblings: a window that reopens off-screen after a
dock is unplugged, an action reachable only by mouse, and a screen reader that
sees one opaque rectangle where the app is.

## Requirements you own

| REQ ID | What it means for you concretely |
|--------|----------------------------------|
| REQ-UI-01 | You implement against the framework `build/scope.md` names, default `eframe 0.36.2` from the manifest. You do not choose it and you do not add a second UI crate. |
| REQ-UI-02 | System chrome by default. If intake chose a custom title bar, every row of `spec/app-surface.md` §1 is implemented — `HTMAXBUTTON` for Snap Layouts included — through `ffi::window`, never a local `unsafe` block. |
| REQ-UI-03 | Persist `WINDOWPLACEMENT` plus monitor device name, work area and the DPI the size was taken at. Restore via `MonitorFromRect(MONITOR_DEFAULTTONULL)`, fall back to primary, rescale the logical size, clamp so 48 px of title bar and 120 px of width stay on-screen. Save debounced 500 ms and forced on `WM_ENDSESSION`. |
| REQ-UI-04 | Every registered action reachable by keyboard, the accelerator table in §3 honoured, a 2 px `focus.ring` indicator shown on keyboard focus and never globally suppressed. The registry records the intended tab order; a test walks it. |
| REQ-UI-05 | AccessKit through eframe's `accesskit` feature, on, non-negotiable. Name, role and value on every control from the string catalogue; state changes through a polite live region, failures through an assertive one, debounced and de-duplicated. |
| REQ-UI-06 | No file, network, registry or process I/O in `crates/ui`, no lock held across a frame, no `sleep`. Work goes to the `TaskSpawner`; `Progress`/`Done`/`Failed` drain once per frame; every task has a `CancellationToken` and a cancel control enabled the instant it starts. Skeleton at 150 ms, spinner at 600 ms, elapsed time and cancel in the foreground at 10 s. |
| REQ-UI-07 | `ViewState` has five variants and the registry refuses a view that does not render all five. `Empty` states why and offers one action; `Error` shows a support-searchable code; `Offline` states when data was last good. |
| REQ-UI-08 | No user-visible literal in a view. `StringKey` generated by `build.rs` from `strings/<base>.json`, so a missing key is a compile error. Locale from `ffi::locale::user_default()`, per-key fallback, in-app override. One formatter for dates, times and numbers. |
| REQ-UI-09 | The six settings sections of §8, hosted by you, each panel contributed by the crate owning the domain. You own the shell and the registry, not another agent's panel content. |
| REQ-TRY-03 | The close-behaviour setting and the one-time explanation, including the in-window fallback shown *before* the window hides when notifications are suppressed. B06 owns the tray; the window side is yours. |
| REQ-DSN-04 | Theme follows the system preference, switches live on `WM_SETTINGCHANGE` with no restart, and is overridable to fixed light or dark in Appearance. |
| REQ-DSN-08 | Reduced motion and high contrast respected: animations off, and in high contrast the palette is replaced from system colours rather than tinted. |
| REQ-DSN-09 | No raw colour literal anywhere in `crates/ui`. Every colour comes from `design-tokens`. A hex literal is a lint failure, not a review comment. |
| REQ-DSN-10, REQ-DSN-11 | Every control has rest, hover, focus-visible, active, disabled, busy and error styling, correct from 100% to 250% DPI and across a drag between mixed-scale monitors. |
| REQ-CTR-05 | You build against `contracts::fixtures`, never against another Wave 3 agent's running code. You wait on nobody. |

## Files you own

- `crates/ui/**`

You write nowhere else. Writing outside this list is a build defect, not a merge
conflict. `crates/tray/**` is B06's, `crates/design/**` is B03's, and a settings
panel belonging to another domain is contributed by its owner through the
registry you publish.

## Contract you publish

`view-registry` and `settings-registry`.

```rust
// crates/ui/src/declaration.rs
#[non_exhaustive]
pub enum ViewState<T> {                                  // REQ-UI-07
    Empty   { reason: EmptyReason, primary_action: Option<ActionId> },
    Loading { started: Instant, determinate: Option<f32> },
    Error   { code: ErrorCode, message: StringKey, retry: Option<ActionId> },
    Offline { last_success: Option<SystemTime> },
    Ready(T),
}

pub struct ViewDef {
    pub id: ViewId,
    pub title: StringKey,                                // REQ-UI-08
    pub actions: &'static [ActionDef],                   // REQ-UI-04, in tab order
    pub accel: &'static [Accelerator],
    pub renders_all_states: bool,                        // registry rejects false
}

pub struct PanelDef {                                    // REQ-UI-09
    pub section: SettingsSection,                         // Appearance | Startup | Updates
    pub id: PanelId,                                     //  | Service | Diagnostics | About
    pub owner: &'static str,                             // "B12" — the contributing agent
    pub render: fn(&mut Ui, &mut PanelCtx),
}

pub fn register_view(def: ViewDef) -> Result<(), RegistryError>;
pub fn register_panel(def: PanelDef) -> Result<(), RegistryError>;  // duplicate id → Err
```

`register_view` returns `Err` for a view that does not render all five states, and
`register_panel` returns `Err` on a duplicate `PanelId` naming both owners — the
same discipline B02 applies at the freeze, applied at runtime to late additions.

## Contract you consume

  You invent none of them, and the mockup a human approved at H1 is the reference
  the result is checked against (REQ-MOC-08).
- `config`, `version`, `errors` (B02) and `paths` (B01).
- `ffi::window`, `ffi::locale`, `ffi::dialog` (B01). A missing wrapper is a CCR
  to B01 (REQ-CTR-07).
- `contracts::fixtures` for everything owned by another Wave 3 agent:
  `fixtures::tray_state()`, `fixtures::service_state()`,
  `fixtures::update_status()`, `fixtures::diagnostics_snapshot()`. You render
  against those, so you never wait on B06, B08, B09 or B12 (REQ-CTR-05).

## How to work

1. Read `spec/app-surface.md` §1–§8, `build/approvals.md` for the named design
   direction, and the token module. Diff your intended layout against the winning
   mockup before writing a view.
2. Build the shell: window creation with system chrome, the message loop, the
   theme watch, and placement save/restore including the lost-monitor path. Write
   that test first — it is the one requirement here with a defined wrong answer.
3. Write `build.rs` for the string catalogue and generate `StringKey`. Add no
   i18n dependency; an ICU-grade need is a CCR to B16 (REQ-VER-02).
4. Stand up the view registry with the five-state enforcement, then one real view
   through all five states before adding a second.
5. Wire the `TaskSpawner`: bounded channel, per-frame drain, `CancellationToken`
   per task, cancel control enabled at task start. Add the banned-symbol lint
   over your own crate in the same commit, so the rule is enforced from the first
   view rather than retrofitted.
6. Enable the `accesskit` feature and give every control a name, role and value.
   Run Narrator over one flow immediately — an accessibility tree added at the
   end is a rewrite.
7. Build the settings shell and the six sections. Publish the registry, then
   contribute only your own Appearance and About panels.
8. Implement the close-behaviour setting and the one-time explanation with its
   in-window fallback (REQ-TRY-03).
9. Run the DPI pass at 100/150/200/250% and drag a window between mixed-scale
   monitors. Hand B15 the capture list: every view, every state, both themes.
10. Grep your own crate for hex literals and user-visible literals before
    handing off. Finding them yourself costs one round less than D1 finding them.

## Definition of done

- [ ] `cargo test -p ui` passes, including: placement round-trip with a saved
      monitor absent from the current layout; a size saved at 200% restored at
      100%; the tab cycle reaching every registered action; five-state coverage
      for every registered view; string-key coverage for every shipped locale.
- [ ] The banned-symbol lint over `crates/ui` reports nothing: no `std::fs`,
      `std::net`, `ureq`, `std::thread::sleep`, `block_on`, blocking `rfd`
      (REQ-UI-06).
- [ ] `grep -rnE '#[0-9a-fA-F]{6}' crates/ui/src` returns nothing (REQ-DSN-09),
      and no `windows` import exists in `crates/ui/Cargo.toml` (REQ-FND-03).
- [ ] A test drives a 3-second task and asserts frame time stays under 8 ms
      throughout and that cancel takes effect within 200 ms (REQ-UI-06).
- [ ] `register_view` rejects a view missing a state and `register_panel` rejects
      a duplicate `PanelId`, both asserted by test (REQ-UI-07, REQ-UI-09).
- [ ] An Accessibility Insights tree dump shows a named control for every action
      id, and a recorded Narrator pass covers the primary flow (REQ-UI-05,
      REQ-TST-09).
- [ ] Theme switches live when the system preference changes, with no restart and
      no flash of the wrong theme, captured in both directions (REQ-DSN-04).
- [ ] High contrast replaces the palette rather than tinting it, captured
      (REQ-DSN-08).
- [ ] B15's capture set exists for every view in all five states in both themes,
      plus the 100/150/200/250% matrix and the mixed-scale drag (REQ-TST-04,
      REQ-TST-08).
- [ ] `git status --porcelain` shows nothing outside `crates/ui/`.

## Hand-off

`build/ui-surface.md` — the view list with its states, the action and accelerator
table, the tab order per view, the six settings sections with the owner of each
panel, and the capture list B15 works from.
`view-registry` and `settings-registry` — consumed by B06 for the menu's Open
action and by B08, B09 and B12 for their panels.
Open CCRs to B01 for any `ffi::window` wrapper you needed, each naming the Win32
call and the reason.

**Every hand-off carries your token usage (REQ-COST-01).** Write
`build/agents/B05/report.json` with your wave, task id, round, the REQ IDs you
claim, and a `usage` block with input, output, cache-read and cache-write tokens
plus the model and effort you ran at. Where your runtime does not expose a count,
write `null` — **never `0`**. A zero is a claim that deflates a total someone
will trust; `null` reads as `unreported` (REQ-COST-04).

**Every hand-off also carries its validation block (REQ-VAL-02).** Before you
write the report — not before you started, not in an earlier round — run
`cargo xtask validate -p <your crate>` and put what it returned into the report:
the command, the exit code, the sha, `cargo test`'s own passed/failed/ignored
counts, your suppression counts (`#[allow]`, `unsafe` blocks, `#[ignore]`,
`.expect()` on a fallible path), the output tail verbatim, and a `redFirst` entry
for every REQ you claim satisfied.

`redFirst` cannot be produced afterwards: it names the sha at which the test
**failed**, for the stated reason, before the code existed (REQ-TST-10). A test
authored against code that already passes it asserts that code's present
behaviour, which is a different claim from the requirement it cites.

The orchestrator reads this block mechanically and re-dispatches on a missing,
red, stale-sha or ignore-carrying one (REQ-VAL-03). It does not read your diff to
decide whether the work probably compiled — a non-zero exit code means everything
else in your report describes a tree that does not exist. And you never write "it
compiles", "the tests pass" or "this still works" without a command that produced
that result in this session (REQ-VAL-04).
